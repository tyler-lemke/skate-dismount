## Why launch provenance matters

A user can report unchanged bugs after source fixes because Play.command opens an older bundle.
The current old ZIP is healthy; stale content and physical corruption are different diagnoses.
A candidate is valid only for the source/assets digest that was tested.
Building again after native validation would silently create a different unvalidated artifact.
Promote the verified bytes, then verify the promoted artifact identity independently.
Keep a previous release backup so a packaging regression is reversible.

## Launcher contract

A downloaded app/ZIP launches the packaged PCK it contains and displays its build ID in diagnostics.
The workspace Play.command resolves paths relative to itself, including paths with spaces.
When source and app identities match, launch the verified bundled app normally.
When source changed and the local Godot 4.7.2 is available, launch current source explicitly
and print a concise development-source/build-identity message before opening the window.
When source changed and Godot is unavailable, report that the bundled game is older and
provide the exact rebuild/development command; do not silently label it the repaired source.
Supply a separate Development.command or documented command for deliberate source launch.
Do not require the user to decide whether the engine mismatch is safe.
Use the supported installed version or a clear actionable version requirement.
Never inject --test-mode, capture, self-check, or temporary record paths into ordinary play.
Do not erase, relocate, or overwrite the player's user:// records to make launch pass.
A packaged app is runnable without a Godot/Blender installation, as before.

Choose identity-aware launch rather than always preferring source because the standalone
package is the player product, while source edits must not masquerade as the same tested build.
This avoids loading an obsolete release and makes future bug reports reproducible.
